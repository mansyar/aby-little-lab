## Changelog — Game 25: Repeat Machine (2026-11-28)

> **2026-11-28 — Repeat Machine:** Game 25 joins the Early programming domain beside Robot Path and Fix-It Machine. A child picks one of four mascot moves and an exact count of two, three or four, then plays the whole move program to watch the mascot repeat it; the target dots ramp across six authored rounds, and a wrong count draws a replay cue so the sequence can be retried without a fail state. It extends `ChoiceRoundScene` with a scene-owned whole-run resolve, is adaptive through `getAdaptiveBandShift`, and has its own audio identity. The new tile joins the Thinking group and the 25-tile Hub, paging and Learning Progress lists; its face comes from existing tile, sticker, glyph and mascot art and its sounds from the shared narrator, so no new texture tier or audio asset was added. Product truth: PRD §2.2 and §3.25; implementation: TDD §4.5, §6 and §10.2; texture re-baseline: [`docs/perf-baseline.md`](./perf-baseline.md) (321 SVGs, 76.42 MiB typical against the 80 MiB cap, 321.00 MiB full against the 322 MiB cap, ratio 0.238).

## Changelog — Game 24: Fix-It Machine (2026-11-16)

> **2026-11-16 — Game 24 — Fix-It Machine:** the suite's first debugging game, and
> the only one where the program is written for the child and the wrong step is the
> puzzle. A tape of instruction cards repairs a toy, one card every 550 ms; exactly
> one card is a substitution, so the machine produces a funny result and stops. The
> child taps that card, picks the tool it should have been from three, and runs the
> tape again to make the toy. Not a loop: the child is reading a program someone
> else wrote and locating its one fault, which is the prerequisite skill a
> programming game assumes. Six fixed rounds of 3, 3, 4, 4, 5 and 5 cards over six
> toys; the wrong card is never the first and its tool never appears elsewhere on
> the tape, so the wrong step always follows a correct one and the diagnosis has one
> answer. The ladder is how close the wrong tool sits — a family the routine never
> uses, then a family it does, then the sibling of the right action — not how many
> cards there are. A stopped run keeps the tape, the round and the child's input
> exactly as they were and rings the wrong card, so the funny result is the
> diagnosis rather than a penalty; hints pulse at two, four and six missed taps and
> never place a card. Hub grid 24 tiles (rows 6/6/6/6, phones 10 + 10 + 4); Settings
> Learning Progress rows 23 → 24 (pages 6+6+6+6); the `thinking` group holds eight
> games; the boot shell gains two keys (tile and sticker) and the sixteen machine
> drawings ride the game's own chunk. Not part of Adaptive Difficulty: the ladder is
> fixed. Hub tiles and stickers are unchanged for every earlier game, and no stored
> id, sticker or profile changes meaning.

## Changelog — Game 23: Robot Path (2026-11-16)

> **2026-11-16 — Game 23 — Robot Path:** the suite's first programming game, and
> the one game whose answer is a program rather than a tap. The child taps
> absolute direction arrows (up, right, down, left) into a six-slot strip to walk
> a robot across a 3×3 board to its star; a dotted ghost trail shows where the
> current program would go before anything moves, and Go replays it at 450 ms per
> step. Commands are absolute rather than forward-and-turn because that is the
> under-five failure mode in Bee-Bot studies — a turn needs a frame the child has
> not built yet. Illegal steps (off the board, into a rock, past the star) are
> refused at placement, so a program can never be invalid; a run that stops short
> keeps every command and pulses the arrow that first left the route, so one arrow
> can be dropped and the same round run again, and after two stopped runs the first
> correct arrow pulses as a hint that is never placed for the child. Six fixed
> rounds, two to six commands each. Hub grid 23 tiles (rows 6/6/6/5, phones
> 10 + 10 + 3); Settings Learning Progress rows 22 → 23 (pages 6+6+6+5); the
> `thinking` group holds seven games; the boot shell gains two keys (tile and
> sticker) and the six robot drawings ride the game's own chunk. Not part of
> Adaptive Difficulty: the ladder is fixed, because the child's own program is the
> difficulty. Hub tiles and stickers are unchanged for every earlier game, and no
> stored id, sticker or profile changes meaning.

## Changelog - Session Lifecycle Integrity (2026-10-22)

> **2026-10-22 — Session Lifecycle Integrity:** Session-lifecycle defects fixed in the shared base class, not per scene. (1) **Progress dots fill on every visit**: `GameSceneBase.createProgressDots` appended to `this.progressDots` without clearing it, and because Phaser destroys display-list children on scene shutdown while the scene instance is reused, the array still held the previous visit's destroyed `Arc` objects at the low indices — `fillProgressDot` mutated those dead objects by index, so the dots the child could actually see never filled. Four games papered over it in their own files; the other eighteen did not, and the child lost all sense of round progress from the second game onward. The base now clears the list when the dots are created. (2) **One wrong-answer reaction**: `GameSceneBase.reactWrong` and `ChoiceRoundScene.handleIncorrect` each played the incorrect tone, recorded the wrong tap, nodded the mascot and ran the same reduced-motion-aware wiggle; the choice-round copy additionally drove a wiggle `onComplete` callback and an overridable `onWrong(index)` hook, and the two had already drifted. The consolidation extends the base helper with that seam rather than swapping blindly, and the shared feedback now plays *after* the scene's own `onWrong` hook, so the incorrect tone lands behind the game's reaction instead of over it. (3) **An abandoned session is not lost**: `completeGame` was the only writer of the session counters, so a child who backed out mid-game lost those taps and the rolling 10-tap window never saw them; the shutdown flush now banks them without double-counting (the completion path is the only cumulative writer and it zeroes the counters, so a reused instance cannot report the same tap twice) and without writing to the wrong profile or game. (4) **The shutdown handler no longer accumulates**: `registerShutdownCleanup` used `events.on` rather than `events.once`, adding one never-removed handler per visit for the lifetime of the scene instance. No new game, no new asset, no change to any round's content, difficulty or pacing.

## Changelog — Audio Variety & Feedback Depth (2026-10-21)

> **2026-10-21 — Audio Variety & Feedback Depth:** All 22 mini-games now carry a fixed sonic identity for the feedback trio (correct / incorrect / win), resolved by the existing Web Audio synth — no new audio assets, no new cue types, no BGM change. `src/game/audioIdentity.ts` holds one central table mapping every `GAME_REGISTRY` gameId to an identity (a pitch offset in semitones, a waveform, a tempo multiplier and its own three melodic contours), with a documented default for unknown ids; `AudioManager` resolves the trio through the requesting scene's gameId at play time, and `GameSceneBase` registers and clears the game context on init and shutdown, so no scene was edited. The parameter space is bounded: pitch offset ≤ 5 semitones, tempo clamped to 0.75–1.5×, the incorrect contour forced gently descending so the no-fail rule holds in every game, and the win cue clamped to end inside 300–800 ms. The default identity reproduces the previous trio exactly (the C5/E5/G5 chime, the G4→C4 descent, the win arpeggio ending at 0.55 s), so the change is character, not loudness. Identities were formula-derived for all 22 games and then tuned by ear. `pop`, `wake`, `sticker`, the frog notes and the BGM stay universal.
